# 独立検証 3 — 座標・地名索引・再修正の再点検

対象: `yagiyagisansam/calc-toolbox` / `claude/stargazing-spot-site-uijopc`

検証日: 2026-08-15

基準コミット: `4c635b1`

## 結論

今回の17件には、単なる市区町村欄の誤りよりも、地点名に対して座標が大きく外れているものが多い。公式ページまたは公式ページが埋め込む地図から、13件は候補地点または具体化先の代表点を確定できた。残る4件は、候補名が広域名・無名の路肩・別地点の混合であり、座標だけを直すことはできない。

ただし、第三者サイトを同一サイトあたり数回までとする制約を優先し、確定後の全地点を国土地理院逆ジオコーダへ再送することはしなかった。下表の `muniCd` は公式所在地に対応する期待コードであり、API応答を得たと偽ってはいない。Claude は候補JSONへ反映する前に、`verify_candidate_cities.mjs` を一度だけ実行して最終確認すること。

実装面では、前回10項目の主要な修正はコードに入っているが、新たに次の問題を確認した。

1. `sandbox="allow-scripts allow-same-origin"` の同一生成元 iframe は、悪意ある子を親から隔離しない。Trusted Types を親へ戻したことには「MapLibre の通常動作を親文書から外す」効果はあるが、MapLibre/子文書が乗っ取られた場合のセキュリティ境界にはならない。
2. 「良い条件がN時間続く」は、1時間ごとのサンプル数を時間数として数えている。連続2サンプルは時間幅1時間であり、表示は1時間過大になり得る。
3. 集落索引は一度ロードされると、主索引が1件以上返す検索にも最大12件まで混ざる。説明されている「主索引が0件のときだけ」と実装が一致しない。
4. 地名補完で日本語別名を1個に潰す設計が残っており、阿蘇山だけの個別修正では再発を防げない。

- 最優先: 自治体・都道府県・国の公式ページに記載された地点、住所、公式ページの地図リンク。

### 推奨する補完設計

座標を手書きする代わりに、補完レコードを次の形にする。

```js
{
  name: "美ヶ原",
  kana: "うつくしがはら",
  source: "gsi-address-search",
  query: "美ヶ原",
  expectedTitle: "美ヶ原",
  expectedPref: "長野県",
  expectedMuniCodes: ["20202", "20350"]
}
```

ビルド時に国土地理院地名検索を1回取得し、次をすべて満たすものだけ採用する。

1. 表示名が完全一致する。
2. 種別が期待する地形種別と一致する。自治体・集落で代用しない。
3. 逆ジオコーダの県・市町村が許容集合に入る。
4. 生応答、取得日、URL、SHA-256を fixture として保存する。
5. 0件または複数件ならビルドを止め、人が候補の意味を決める。

国土地理院「地名集日本」は政府標準地名・座標・種別を持つため第一候補の補助資料だが、約4,100件の全国主要地名に限られ、今回の4語はPDF内で完全一致を確認できなかった。これだけを万能な補完元にはできない。https://www.gsi.go.jp/kihonjohochousa/gazetteer.html

### 別ファイル446KBの評価

446KB gzipを、主索引0件のたびに自動取得する現設計はそのまま承認しない。

- 入力途中の一時的な0件・誤字でも取得が始まる。古い問い合わせ結果は表示時には捨てているが、通信開始自体は止まらない。
- 一度ロードすると `Places.search()` は主索引が1〜11件ある検索にも集落を追加する。コメントの「主索引で0件のときだけ」と不一致。
- 46,000件を以後の全入力で線形走査する。PC実測では約0.25〜0.7ms/検索だったが、低速iPhone・メモリ使用量・JSON parseは別に測る必要がある。
- 集落索引に読みがなく、かな入力で小地名を探せない。

最小修正案は、(a) 300〜500ms debounce、(b) 正規化後2文字以上、(c) 主索引0件のときだけ検索結果へ混ぜる、(d) ロード後も同条件を維持、(e) 「小さな地名も検索する」明示操作を用意すること。都道府県選択済みなら県別ファイル、未選択なら明示操作にする設計が通信量と予測可能性のバランスがよい。

## C. 前回10項目と追加実装

### C-1. Trusted Types / iframe

判定: **親文書へTrusted Typesを戻したことは局所的な改善だが、iframeをセキュリティ境界と説明してはいけない。**

`allow-scripts` と `allow-same-origin` を同じ生成元のiframeに同時指定すると、子は親と同じoriginを持ち、`window.parent.document` へアクセスできる。子が乗っ取られれば、親のDOM操作、親関数の呼び出し、同一生成元の権限での通信が可能である。さらに子は親DOM上のiframeの `sandbox` 属性を外して再読込できる。このため、現在のsandboxは悪意ある子の封じ込めではなく、通常動作でのトップ移動・ポップアップ・フォーム送信を抑える程度のもの。

`postMessage` の `source` と厳密な `origin` の検査は、通常のメッセージ偽装には正しく効く。ただし、乗っ取られた同一生成元の子はpostMessageを使わず親へ直接触れられるので、侵害時の防壁にはならない。

意味のある分離にする選択肢は次の順。

1. 地図文書を専用の別originへ配信し、親子のoriginを分ける。親は固定した子originだけを許可し、子も固定した親originだけを許可する。
2. 別originが用意できないなら、MapLibre側でTrusted Types対応版・限定default policyを検討し、親文書内で必要sinkだけを許可する。
3. どちらもできなければ、現状を「セキュリティ境界」ではなく「依存コードとDOM sinkの整理」と文書化し、MapLibre/worker/styleの供給経路・更新手順・ハッシュを厳格にする。

`index.html` は最も利用される画面で、MapLibreと同居するためTrusted Typesなしのまま。受け入れるなら、一覧・詳細・申請だけを守った部分適用であることを脅威モデルに明記する。サイト全体で復旧したとは表現しない。

追加の入力検証:

- 親側 `submit.js` の `pick(lat, lon)` は最初に `Number.isFinite` を確認すべき。`NaN` は全境界比較をすり抜ける。
- `pick.js` の `init`/`mark` はlatだけでなくlonも有限値か確認し、緯度・経度の物理範囲も検証する。
- これは同一生成元の悪意ある子への防壁ではないが、壊れたメッセージと将来のorigin分離に備えた契約として必要。

### C-2. 月の地点別補正

`map.js` は月係数を天気格子上で地点別に計算し、画素ごとに双一次補間するよう変更されている。中心点1個の値を全国へ掛ける前回の欠陥は解消している。`sky.test.mjs` の南北差検査も実際の期待値差を持つ。

注意点: `moonFactorAt()` は格子外座標で行・列だけをclampし、補間係数 `wx/wy` はclampしない。現在の描画範囲内では直ちに表面化しないが、検証用APIとして格子外を渡すと外挿値になる。テストまたは引数範囲の明示が必要。

### C-3. 月fixtureの来歴

問い合わせパラメータ、API version、応答SHA-256、応答byte数、取得日時は保存され、前回より追跡可能になった。テスト値を実装自身から作る循環も解消している。

ただし、生応答そのものは保存されていないため、保存済みSHA-256を後から再計算してfixtureの由来を証明することはできない。APIが将来違う値を返すと、過去応答のハッシュは比較対象がない。完全な来歴が必要なら、生応答を圧縮fixtureとして保存するか、取得結果を改変不能なリリース成果物へ添付する。

### C-4. continuity表示

`list.js` と `spot.js` は1時間ごとの「合格サンプル数」をそのまま時間数としている。例:

- 01:00だけ65点以上 → 「1時間続く」
- 01:00と02:00が65点以上 → 「2時間続く」

しかし観測点間の確定時間幅としては後者が1時間であり、前者は継続時間を確定できない。予報の刻みが将来30分や3時間になっても誤る。

`times[i+1]-times[i]` から区間を作り、隣接する両端が閾値以上の区間だけを加算するか、「良い予報枠がN個」と表示する。利用者向けには前者がよい。境界を線形補間しない限り「約N時間」とする。

### C-5. 差分SQL

324項目の比較へ拡張した方向はよい。列、制約、索引、関数定義、権限、RLS、policy、triggerを比較している。
