## 0. いちばん大事なこと

**私の検証には循環しているものがあります。** 期待値を自分の実装で計算して
テストに書いた箇所があり、その部分は「実装が仕様どおりか」ではなく
「実装が実装どおりか」しか確かめていません。**外部の権威ある情報と突き合わせて
ください。** どこが循環しているかは §3 に明示します。

「全部通りました」という報告は要りません。**間違いを見つけてください。**

## 3. 独立に検証してほしいこと（優先順）

### 3-1. 天体計算 ── ★最優先・循環あり

`stars/sky.js` は Meeus『Astronomical Algorithms』の簡略式で
太陽・月の位置、月齢、天文薄明を計算しています。

**`stars/tests.json` の期待値のうち、月の高度・太陽高度・夜の長さは
私が自分の実装を走らせて得た値をそのまま書いています。** つまり実装が
間違っていてもテストは通ります。

- 国立天文台 暦計算室（`https://eco.mtk.nao.ac.jp/koyomi/`）などの
  独立した情報源と突き合わせてください。
- 特に見てほしい: 月の出入り（`moonRiseSet`）、天文薄明の判定
  （太陽高度 −18°、`nightWindow`）、月齢と輝面比。
- 許容誤差の考え方：月の位置は角度で 0.3° 以内、月齢は 0.2 日以内を想定。
  これで星見の可否判定に足りるか、判断も含めて意見をください。

### 3-2. 「今夜」の判定 ── 境界条件

`Sky.currentNightDate(lat, lon, now)` は「いま見るべきは何日の夜か」を返します。
夜は日付をまたぐため、深夜0時や明け方に誤りやすい箇所です。
一度バグを出して直した経緯があります（「正午より前なら前日」という
時刻での線引きが誤りだった）。

- 日付変更をまたぐ時刻、薄明が始まった直後、日没直前で総当たりしてください。
- 端末のタイムゾーンが日本以外でも正しいか（実装は端末TZに依存しない
  つもりですが、確認してください）。

### 3-3. 投影のずれ ── 見た目では気づけない

`stars/map.js` の描画。光害ラスタは**緯度が等間隔（正距円筒）**、
MapLibre の canvas ソースは**Webメルカトルで線形**として貼られます。
変換を1か所でも誤ると南北にずれますが、見た目では気づけません。

- `buildCanvas` の `mercY` / `invMercY` と行ごとの緯度の対応を追ってください。
- 既知の座標（例：東京 35.68/139.76、稚内 45.42/141.67、石垣 24.34/124.16）で
  canvas の画素が正しい段階になるか、独自に検算してください。

### 3-4. 海上の格子を落とした件 ── 証明が正しいか

`scripts/stars/land_grid.mjs` で、天気を取りに行く地点を 552 → 325 に削減しました。

私の主張：「陸の描画は1ドットも変わらない。画面の1画素は囲む4つの格子点から
双一次補間で作られるので、**陸から1度以内の格子点をすべて残せば**陸の値は不変」。
海岸線の全頂点（15,840点）について「囲む4点が残っている」ことを検査しています。

- **この論法自体が正しいか**を検証してください。格子の刻みは1度、
  補間は双一次です。反例（陸の画素が、落とした格子点を参照するケース）は
  作れませんか。
- 落とした地点には最も近い取得地点の値を複製しています。
  地図では海に色を塗らないので表示に影響しないはずですが、
  **本当にどこにも漏れていないか**（一覧・詳細・申請ページの計算を含む）。

### 3-5. スコアの設計 ── 妥当性の判断

`stars/score.js`。光害・雲量・降水確率・視程・湿度・月を**掛け算**で合成し
0〜100 にしています。しきい値と `darknessAnchors`（光害の指標値→暗さ）は
私が参照地点を選んで決めたもので、**外部の根拠はありません**。

- 掛け算で合成する設計の是非。
- 6段階の区切り（80/65/50/35/20）の妥当性。
- 天文の常識に照らして明らかにおかしい振る舞いがないか
  （例：満月・快晴・暗所 と 新月・薄曇り・郊外 の順序関係）。

### 3-6. サーバー側SQL ── 張りぼてでしか試していない

`scripts/stars/weather-cache.sql`。pg_cron + pg_net で天気を定期取得し、
1行のキャッシュに入れて全員に配ります。

**私の検証はローカルの PostgreSQL に pg_cron / pg_net の代役を作って行ったもので、
本物の pg_net の挙動（応答の保持期間、状態遷移、並行実行）は再現していません。**

- 応答が消えた/重複した/順序が入れ替わった場合の `stars_weather_collect` の挙動。
- 取り直し（`stars_weather_retry_one`）が無限に投げ続ける経路が無いか。
  1日60回の上限で縛っていますが、抜け道はありませんか。
- 「同じ周回は取り込まない」判定（`meta.cycle`）に競合はありませんか。
- 6分割の連結順が壊れる経路（分割数を変えた直後など）。

### 3-7. セキュリティ ── 実測済みだが再確認を

匿名キーは誰でも入手できる前提です。本番へ実際に問い合わせて、
内部テーブル6つ・内部関数8つがすべて拒否されることを確認済みです。
到達できるのは `stars_public_spots()` と `stars_weather_cache` の読み取りだけ。

**ここは実測しているので信頼度は高いですが、見落としを探してください。**

- 画面側に `innerHTML` は1か所もありません（`textContent` のみ）。
  外から来た文字列が属性に入る唯一の場所は `spot.source_url` → `a.href` で、
  データベース側のトリガ（https のみ）と表示側の `isSafeUrl()` で二重に守っています。
  **他に見落とした sink はありませんか。**
- CSP は `default-src 'none'` 起点、`script-src 'self'`、`style-src 'self'`
  （`unsafe-inline` なし）。地図を読まない3ページには
  `require-trusted-types-for 'script'` を追加。
- GitHub Pages はヘッダーを送れないので `frame-ancestors` が使えず、
  `stars/guard.js` で枠内表示を拒んでいます。**この方法で足りますか。**
- 既知の限界：端末識別子は自己申告なので「24時間3件」は回避可能。
  全体の「1時間100件」上限と、全件が管理者承認制であることで担保しています。

### 3-8. 表示と文言

- 一覧と詳細で同じスポットのスコアが一致すること（一度ずれていて直しました）。
- 予報が今夜を賄えていないとき、黙って部分データを描いていないこと。
- 「データについて」の記述が実装と食い違っていないこと。

## 4. やってはいけないこと

1. **公開しない。** `main` へのマージ、`gh-pages` への push は禁止です。
   （このリポジトリは `git push origin main:gh-pages` で公開されます）
2. **`claude/stargazing-spot-site-uijopc` 以外のブランチへ push しない。**
3. **Supabase に書き込む関数を呼ばない。**
   `stars_weather_request` / `collect` / `retry_one` / `grid_build` /
   `stars_ops_*` は本番の状態を変えます。読み取りだけにしてください。
4. **掲載スポットを追加しない。** 掲載は管理者（Hiroさん）の承認制です。
5. **Open-Meteo を大量に叩かない。** 無料枠は1日10,000回で、定例の取得が
   4,550回を使っています。検証で叩くなら数回に留めてください。
6. **`service_role` キーをリポジトリに書かない。** 公開用の anon キーだけです。

## 5. 報告してほしいこと

見つけた問題ごとに：

1. **どこ**（ファイルと行）
2. **何が起きるか**（具体的な入力 → 誤った出力。再現手順）
3. **なぜそうなるか**
4. **どう直すべきか**

「問題なし」の項目は列挙不要です。**§3 のうち検証しなかった項目があれば、
その旨だけ書いてください**（黙って飛ばさないでください）。

判断が分かれるもの（スコアの設計など）は、断定せず根拠を添えて意見として
書いてください。
